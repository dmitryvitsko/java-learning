# 🥠 Фабрика печенек с предсказаниями — модульное тестирование JUnit

## 📋 Задача
Написать пять unit-тестов для фабрики печенек с предсказаниями.
Проверить работу контроллера и корректность работы фабрики -
типы предсказаний, счётчик испечённых печенек, сброс счётчика.

---

## 🏗 Архитектура

- `FortuneCookieController` - принимает запросы, делегирует работу фабрике
- `FortuneCookieFactory` - печёт печеньки, хранит счётчик
- `FortuneCookie` - сама печенька с текстом предсказания
- `FortuneConfig` - конфигурация фабрики (позитивные/негативные предсказания)

---

## 🧠 Теория

### Аннотация @Test
```java
@Test
public void shouldReturnPositiveFortune() { ... }
```
Помечает метод как тестовый - JUnit найдёт и запустит его автоматически.
Название теста пишется в стиле "should + ожидаемый результат" -
сразу понятно что именно проверяется.

### @BeforeEach — подготовка перед каждым тестом
```java
@BeforeEach
public void beforeEach() {
    fortuneCookieFactory = new FortuneCookieFactory(...);
    fortuneCookieFactory.bakeFortuneCookie();
}
```
Метод выполняется перед КАЖДЫМ тестом заново - гарантирует что
каждый тест стартует с чистого одинакового состояния, а не
зависит от того что осталось после предыдущего теста.

### Проверка через контроллер, а не напрямую через классы
```java
FortuneCookieController controller = new FortuneCookieController(factory);
FortuneCookie cookie = controller.tellFortune();
```
Тесты на FortuneCookieController должны проверять именно
поведение контроллера - что он корректно делегирует работу
фабрике и возвращает результат. Не стоит тестировать внутренние
детали фабрики через контроллер - для этого есть отдельные
тесты на саму фабрику.

### Импорт List и ArrayList — разные вещи
```java
import java.util.ArrayList; // конкретная реализация
import java.util.List;      // интерфейс, нужен для List.of()
```
`List.of(...)` - статический метод интерфейса List. Даже если
результат кладётся в ArrayList - для использования List.of()
нужен отдельный импорт интерфейса List.

### Разные assert-методы под разные проверки
```java
assertTrue(condition);      // условие истинно
assertFalse(condition);     // условие ложно
assertEquals(expected, actual); // значения равны
assertNull(value);          // значение null
assertArrayEquals(expected, actual); // массивы равны поэлементно
```

---

## 🛠 Что использовал
- JUnit 5 - `@Test`, `@BeforeEach`
- Различные assert-методы под разные типы проверок
- Тестирование через публичный интерфейс класса, а не внутренние детали
- Разделение тестов по классам ответственности (Controller/Factory)

---

## 💡 Вывод
Хороший unit-тест проверяет конкретное поведение и может
реально провалиться если код содержит ошибку. Важно тестировать
то что просит задача - если тест на контроллер, значит нужно
вызывать методы контроллера, а не копаться напрямую в его
внутренних зависимостях.
